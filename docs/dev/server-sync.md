# Сервер: зеркало на свой сервер Ampulse

Необязательная выгрузка данных приложения на свой сервер Ampulse
(изменение OpenSpec `server-sync`; сервер — отдельная программа владельца, не входящая в этот репозиторий). **Только сборка `github`**; выключено, пока человек не вошёл; **только с телефона на
сервер** — ничего не скачивается. Приложение без сервера работает как раньше, полностью офлайн.

Зачем: сервер показывает данные другим (страница просмотра, другие телефоны) и шлёт напоминания и сообщения о пропуске
членам профиля. Расписания у приложения богаче серверных (интервалы, циклы, ступени, «по необходимости»), поэтому на сервер
уходит **результат** — конкретные приёмы с временем, а не правила.

## Как устроено

Код — пакет `app/src/main/java/io/github/agitangst/ampulse/sync/`; чистая часть (без Android) покрыта тестами на JVM.

| Файл | Что делает |
|---|---|
| `SyncIds.kt` | Идентификаторы записей на сервере |
| `MirrorModel.kt` | Записи сервера (профиль, лекарство, приём), отпечатки, окно, набор |
| `MirrorBuilder.kt` | Из базы телефона (`SyncSnapshot`) строит набор: раскладывает схемы в приёмы окна, сливает отметки |
| `SyncState.kt` | Состояние выгрузки (что уже на сервере), разница `SyncDiff` |
| `MirrorClient.kt` | HTTP: вход, регистрация, выход, выгрузка; ошибки в виде `SyncFailure` |
| `SyncEngine.kt` | Разница → запросы по 500 → состояние по ответу; стирание |
| `ServerSync.kt` | Android: вход и выход, запуск, хранение (`SharedPreferences`, файл состояния), состояние для экрана |
| `ui/ServerScreen.kt` | Экран «Сервер»; строка в «Настройках» — `SettingsScreen.kt` |

Из базы читает `Repository.mirrorSnapshot` — только чтение, схема Room и миграции не менялись.

## Что выкладывается

Окно приёмов — от начала дня «сегодня − 30 дней» до конца дня «сегодня + 14 дней» в **системном поясе** телефона.

- **Профили.** «Я» (локальный номер 0; имя — строка «Я» / «Me» по языку приложения) и свои профили. Вид: человек →
  `person`; кошка, собака, другое → `animal`. `timezone` — системный пояс (если у него нет региона вида `Europe/Berlin`,
  то `UTC`). `note` пустая. **Копии чужого расписания** (профили `watchOnly`) и их лекарства **не выкладываются**.
- **Лекарства.** `form`: Injection → `injection`, остальные (таблетка, капсула, капли, жидкость, другое) → `pill`;
  `dose` — «дозировка»; `note`; `archived`. Имя режется до 80 знаков, доза и заметка — до 1000 (пределы сервера).
- **Приёмы.**
  - *Плановые*: `Plan.dosesOn` схем не убранных лекарств на каждый день окна. Статус `pending`; есть отметка с тем же
    лекарством и плановым временем — `taken` (с `taken_at` = время отметки) или `skipped` (причина — в `note`).
    `planned = true`.
  - *Отметка без планового приёма*: схему изменили или поставили на паузу, а отметка у времени осталась — выкладывается как
    плановая со своим плановым временем (отметка не пропадает). Архивное лекарство новых плановых приёмов не получает, но
    прошлые отметки остаются.
  - *Внеплановые* (`Extra`, «по необходимости», отметки без планового времени): `planned = false`, `planned_at` =
    `taken_at` = время приёма, `taken`. Внеплановый «пропущено» остаётся `skipped`.
- **Не выкладывается:** аптечка и упаковки, давление, близкие (контакты), экстренная карта, место укола, количество
  (`amount`), правила схем.

**Известное:** прошедшие неотмеченные приёмы окна уходят как `pending` — как в самом приложении («просрочено»). Сервер
Сервер Ampulse (с версии 0.7) приём, который при первой выгрузке уже в прошлом, не объявляет ни напоминанием, ни сообщением о
пропуске, так что первая выгрузка не засыпает членов профиля сообщениями за прошлое; на странице просмотра он виден.

## Идентификаторы

Сервер принимает любые 8–64 знака `A-Za-z0-9_-`. Приложение выбирает:

```text
id = Base64URL(SHA-256(соль ‖ вид ‖ ":" ‖ число ‖ ":" ‖ число …))[0..22]
```

- Соль — 16 случайных байт, создаётся один раз и лежит в приватных `SharedPreferences` (`server_sync`, ключ `salt`).
  На сервер не уходит. Без неё по id нельзя ни узнать номер записи в базе телефона, ни проверить догадку, ни связать
  выгрузки двух телефонов.
- Вид и числа: `profile` + локальный номер профиля (0 — «Я»); `med` + номер лекарства; `event` + номер отметки
  (внеплановые); `plan` + номер схемы + плановое время в **минутах** Unix (плановые приёмы).
- Детерминированность: повторная выгрузка даёт те же id — сервер ничего не задваивает, таблицы соответствий в базе нет.

## Состояние выгрузки

Файл `filesDir/server_sync_state.json` (запись — через временный файл и переименование):

```json
{"v":1,
 "profiles":{"<id>":["<отпечаток>",0,""]},
 "meds":    {"<id>":["<отпечаток>",0,"<id профиля>"]},
 "intakes": {"<id>":["<отпечаток>",<время приёма, с>,"<id лекарства>"]},
 "rejected":{"<вид>/<id>":"<отпечаток>:<код>"}}
```

- **Отпечаток** — SHA-256 содержимого записи. Выкладывается запись, которой нет в состоянии или у которой другой отпечаток.
- **Удаление.** Запись есть в состоянии, но пропала из построенного набора → `delete`. Приёмы — только внутри окна: те,
  что со временем вышли за его начало (старше 30 дней), остаются на сервере. Приёмы старше 400 дней из файла забываются.
- **Состояние меняется только по ответу сервера** и только для записей с `ok`; после каждого запроса файл сохраняется —
  оборванная выгрузка не теряет сделанного.
- **Отказ записи** (ответ `ok: false`): `bad_*` и `text_too_long` — насовсем: запись попадает в `rejected` и не шлётся,
  пока её содержимое не изменится; лекарства и приёмы отклонённого профиля тоже не шлются. Остальные коды (`not_found`,
  `conflict`, `read_only`…) повторятся при следующей выгрузке. Отказы показываются на экране «Сервер» счётом и кодами.
- Файл потерян или испорчен — состояние пустое, всё выложится заново (повтор безвреден), но ранее выложенное и пропавшее с
  телефона на сервере останется.
- Другой сервер или другой аккаунт при входе — состояние сбрасывается (`state_key` = адрес + id аккаунта).

## Протокол

Контракт сервера — раздел «Зеркало» в описании API самого сервера (версия сервера 0.7 и новее).

- `POST /api/v1/login`, `/register` `{login,password}` → `{account_id,token}`; `POST /api/v1/logout`; `Authorization: Bearer <токен>`.
- `POST /api/v1/mirror` `{profiles,meds,intakes,delete:{profiles,meds,intakes}}`. До 500 записей каждого вида за запрос —
  больше режется на части: в каждом круге по 500 каждого вида, порядок внутри запроса задаёт сервер (профили, лекарства,
  приёмы, затем удаления приёмов, лекарств, профилей). Ответ — `results[{kind,id,ok,error?}]` по записи в том же порядке; не
  совпало число или порядок — ошибка сервера (`bad_reply`), состояние не меняется.
- Клиент — `java.net.HttpURLConnection` и `org.json` (из Android), таймауты 10 с / 30 с, перенаправления не выполняются,
  тело в буфере, ответ не больше 4 МБ. HTTPS обязателен: адрес без схемы получает `https://`, `http://` — отказ.
- Ошибки: `401` → `Unauthorized`; `429` → `RateLimited` (`retry_after_secs`); прочие `4xx` → `Rejected(код)`; `5xx` и не-JSON →
  `Server`; обрыв, таймаут → `NoConnection`, неизвестный хост — `host`, ошибка TLS — `tls`.

## Запуск

| Когда | Как |
|---|---|
| «Отправить сейчас» | сразу |
| Открытие приложения (сборка `github`, вошли) | не чаще раза в минуту |
| Изменение данных (`ChangeListener` репозитория: отметка, правка лекарства…) | через 30 секунд, одной отложенной задачей; изменения за это время собираются в один запрос |

Без WorkManager: закрытое приложение ничего не шлёт. Выгрузки идут по одной (мьютекс).

## Вход и выход

- **Войти / Создать аккаунт** — логин (3–32 знака `a-z 0-9 _ . -`), пароль (10–200 знаков); сервер без открытой
  регистрации аккаунт не создаст (`registration_closed`). После входа сразу идёт первая выгрузка.
- **Выйти** — токен отзывается на сервере (если получится) и стирается; выложенное остаётся; состояние хранится, поэтому
  повторный вход в тот же аккаунт того же сервера ничего не задвоит.
- **Выйти и стереть копию на сервере** — `delete` для всего выложенного (по состоянию), затем выход. Не удалось (нет
  связи…) — вход и копия остаются, причина на экране. Токен уже не годится (401) — выход всё равно, копия не стёрта.
- **401 на выгрузке** — токен стёрт, приложение вышло, на экране «Вы вышли… войдите снова» (адрес и логин остаются).
- **Пароль нигде не хранится** и в журнал не пишется. **Токен** — в `SharedPreferences` `server_sync_secret` (приватные,
  только приложение); из правил переноса на другой телефон исключён (`data_extraction_rules.xml`) — там войдите заново.
  Остальное (адрес, логин, соль, счётчики) переезжает вместе с данными; облачная копия не получает ничего.

## Состояния экрана «Сервер»

| Состояние | Что видно |
|---|---|
| Не вошли | вступление (что уходит и что нет), поля «Адрес сервера», «Логин», «Пароль», «Войти», «Создать аккаунт» |
| Вышли сами (401) | плашка «Сервер больше не узнаёт это устройство… Войдите снова», те же поля |
| Вошли | «Подключено», сервер, логин, «Последняя отправка: …», «N записей на сервере», «Отправить сейчас», «Выйти», «Выйти и стереть копию на сервере» |
| Идёт выгрузка | кнопка «Отправляется…» (недоступна) |
| Проблема | плашка: нет связи / сервер не найден / не принят сертификат / слишком много запросов (через N мин) / ошибка сервера |
| Часть записей отклонена | плашка «Сервер не принял: N (коды)…» |

В «Настройках» строка «Сервер» (только `github`): «Выключено…» / «Включено · адрес» / «Вы вышли. Войдите снова».

## Сборки магазинов

`Store.SERVER_SYNC` — `true` в `github`, `false` в `rustore` и `play`. В них строка «Сервер» скрыта, `ServerSync` ничего не
запускает (`available = false`), экран при открытии по устаревшему маршруту закрывается; манифесты по-прежнему снимают
`INTERNET` и `ACCESS_NETWORK_STATE`. В манифесте `github` `INTERNET` объявлен явно.

## Проверка

- Тесты JVM (`app/src/test/.../sync/`): id, построение по всем видам схем (каждый день, по дням недели, раз в N дней,
  циклы, ступени, «по необходимости») с отметками «принято / пропущено / лишний», окно, архивные, профиль «Я», копии чужого
  расписания; различие состояний и удаления; JSON тела; клиент и движок против крошечного HTTP-сервера на
  `com.sun.net.httpserver` (`FakeServer`): вход, выгрузка, 401, 429, обрыв, разбор отказов записей, нарезка по 500, стирание.
  Для JSON в тестах нужна зависимость `org.json:json` (в `android.jar` методы-заглушки).
- Живая проверка против настоящего сервера — `LiveServerTest`; в обычный прогон не входит, включается переменными
  окружения: сервер запускают с `--open-registration` на 127.0.0.1 и задают `AMPULSE_LIVE_URL=http://127.0.0.1:<порт>`
  и `AMPULSE_LIVE_LOGIN`, `AMPULSE_LIVE_PASSWORD` (любые, на один прогон; пароль 10+ знаков; `AMPULSE_LIVE_KEEP` — оставить выложенное). Тест выкладывает
  выдуманные данные, повторяет (ничего лишнего), меняет отметку, удаляет лекарство, сверяет с `GET /api/v1/sync` и
  стирает всё. Gradle считает тест устаревшим только при смене кода — для повторного прогона `cleanTestGithubDebugUnitTest`.
- Не проверено: работа на телефоне (экран в двух темах и двух языках, срок 30 секунд, поворот экрана), настоящий HTTPS с
  сертификатом, поведение при смене пояса и перехода на летнее время.
